# 技术分析 agent — 在 DSH 中内联渲染交易图表

**状态：ready-for-agent**

## 问题陈述 (Problem Statement)

交易者若想快速对加密市场做一次技术面判读，必须打开图表平台、手动添加指标、切换周期，然后自己解读画面。在 AI 聊天中，答案只是纯文本、没有图表，因此人必须把价格、指标数值和价位记在脑中。

无法提出像"今天 BTC 的走势如何"这样模糊的问题，然后拿到一张**在对话内渲染、带指标标注的图表**外加一份分析，也没有指引说明哪些指标才真正适合当前的**市场状态**。如今的聊天 agent 要么根本不画图，要么用别人的数据和别人的指标来画。

## 解决方案 (Solution)

一个以插件形式安装进 DSH 的 agent，它把模糊的加密市场问题变成一张**在对话内渲染的交互式 K 线图**，图上标注主流指标，并附上一份**分层分析**（结构、关键价位、形态），以及基于当前市场状态的**指标推荐**。

它是一个 agent，而不是一张表单：它解析意图、填充默认值（symbol、周期、指标集）、自行获取行情、绘图、分析，并说明自己做了哪些选择。只有当它确实无法解析时，才会向用户询问。

图表基于 **Lightweight Charts** 构建，数据源是**我们自己的** Binance/Hyperliquid OHLCV，因此完全可控，不受第三方数据限制。该插件**开源（MIT）**，任何人都可以安装。

## 用户故事 (User Stories)

### 意图与默认值 (Intent and defaults)
1. 作为交易者，我希望输入像"今天 BTC 走势如何"这样模糊的问题，这样就不必指定 symbol、周期和指标。
2. 作为交易者，我希望 agent 自动把 "BTC" 解析为其主要现货交易对，这样最常见的情形无需澄清。
3. 作为交易者，我希望 agent 把时间词（"今天"、"这周"、"这月"）映射到合适的主要周期，这样图表与我隐含的时间跨度相匹配。
4. 作为交易者，我希望 agent 说明它所选的默认值（symbol、周期、指标），这样如果它猜错了，我可以纠正。
5. 作为交易者，我希望 agent 只在 symbol 完全无法解析时才提问，这样它不会为那些它能推断出来的事情盘问我。
6. 作为交易者，我希望用自然语言覆盖任何默认值（"用 MA50/200 看 BTC 4h"），这样对话保持自然。
7. 作为交易者，我希望 agent 记住对话的上下文（相同 symbol、改变周期），这样后续追问成本很低。

### 数据 (Data)
8. 作为交易者，我希望 OHLCV 数据默认取自 Binance 现货，这样无需 API key 就能获得深厚的历史数据。
9. 作为交易者，我希望 Hyperliquid 作为补充数据源，用于原生永续数据（funding、open interest、mark price）和 HL 上市的资产，这样链上市场也能覆盖。
10. 作为交易者，我希望 agent 按周期缓存响应并使用较短的 TTL，这样重复提问很快，且能遵守速率限制。
11. 作为交易者，我希望 agent 在 Binance 429/418 时正确退避，这样一连串提问永远不会导致 IP 被封。
12. 作为交易者，我希望在某个市场的 Hyperliquid 历史太短、不足以支撑长回看时得到告知，这样不会给我展示误导性的长周期移动平均线。

### 图表 (Chart)
13. 作为交易者，我希望在**聊天消息内部**渲染一张交互式 K 线图，这样我就不必离开对话。
14. 作为交易者，我希望图表可以缩放和平移，这样我能查看细节。
15. 作为交易者，我希望能在图表上切换周期，这样无需重新输入就能在 15m/1h/4h/1d 之间切换。
16. 作为交易者，我希望默认绘制主流指标——价格窗格上的 MA20/50/200，以及下方的 MACD、RSI 和成交量——这样图表立即就有用。
17. 作为交易者，我希望叠加布林带并能逐个开关指标，这样我可以减少杂乱。
18. 作为交易者，我希望形成中（未收盘）的 K 线也显示出来但在视觉上有所区分，这样我能感知实时价格又不会被误导。
19. 作为交易者，我希望在图表上标出规则信号（金叉/死叉、超买/超卖、价位突破），这样机械性事件清晰可见。

### 分析 (Analysis)
20. 作为交易者，我希望得到走势/结构判断，这样我知道方向及其强度。
21. 作为交易者，我希望得到关键价位——支撑、阻力、失效位——这样我知道一个想法在哪里会出错。
22. 作为交易者，我希望识别出被命名的结构与形态及其位置，这样我能看到 agent 在读什么。
23. 作为交易者，我希望每个结论都带有**方向、失效位和置信度（高/中/低）**，这样主观判断是可以被证伪的。
24. 作为交易者，我希望分析只基于已收盘 K 线运行，这样尚未成形的 K 线永远不会触发信号。
25. 作为交易者，我希望多周期共振——用更高周期确定结构和方向，用当前周期确定时机——这样我得到的是上下文，而不只是一张快照。
26. 作为交易者，我希望优先给出走势结构（道氏 HH/HL/LH/LL、均线排列、走势线/通道）以及支撑/阻力/斐波那契，这样在进行更主观的形态工作之前基础是牢固的。
27. 作为交易者，我希望把经典形态（头肩、双顶/双底、三角形、旗形）作为第二层，这样图表形态也能覆盖。
28. 作为交易者，我希望艾略特波浪放在最后，这样最主观的方法不会锚定整个分析。
29. 作为交易者，我希望 agent 区分机械性候选与它自己的判断，这样我能分辨哪些是计算出来的、哪些是解读出来的。

### 市场状态与指标推荐 (Market state and indicator recommendation)
30. 作为交易者，我希望得到一个机械计算的**市场状态**（走势强度、区间与趋势之别、波动率、成交量状态、均线排列），这样分析锚定在可度量的上下文中。
31. 作为交易者，我希望 agent 推荐适合当前市场状态的额外指标，这样我能学到当下真正有信息量的东西。
32. 作为交易者，我希望指标推荐只是建议性文本，这样在我没有要求时图表不会被弄乱。
33. 作为交易者，我希望用一条消息接受一项推荐并让它被绘制出来，这样采纳建议毫不费力。

### 感知 (Perception，可选视觉)
34. 作为交易者，我希望 agent 默认基于数值数据进行推理，这样它在任何模型配置下都能工作。
35. 作为交易者，我希望当某个主观的形态判断需要"眼睛"时，agent 额外把图表栅格化为图像，这样形态判读更强。
36. 作为交易者，我希望当我的模型路由仅支持文本时，插件能优雅降级到数值路径，这样不会有任何东西出问题。
37. 作为交易者，我希望通过一个有文档的 harness 设置来选择启用视觉，这样是否启用由我决定。

### 分享与运维 (Sharing and operation)
38. 作为交易者，我希望按包名安装插件，这样安装只需一条命令。
39. 作为开发者，我希望插件以 MIT 开源，这样我可以阅读、fork 并扩展它。
40. 作为开发者，我希望插件不需要任何 API key，这样分享它不花任何人任何成本。
41. 作为开发者，我希望插件附带构建好的宿主与客户端 bundle，这样无需本地构建步骤即可工作。
42. 作为开发者，我希望有一个随附的 skill 教会模型何时以及如何使用这些工具，这样行为保持一致。
43. 作为开发者，我希望宿主↔客户端契约是单一可序列化的图表规格，这样两半可以独立演进。
44. 作为开发者，我希望数据提供方位于同一接口之后，这样新增交易所是增量式的。

## 实现决策 (Implementation Decisions)

### 平台与分发 (Platform and distribution)
- 产品是一个**双面 DSH 插件**：宿主半边（Node/TypeScript，一个注册工具的 Cordis 插件）和客户端半边（一个浏览器 React 组件），由同一个 npm 包发布，该包声明 DSH bundle patch 和客户端 manifest。
- 它以 **MIT 开源**，发布到 npm，可通过 DSH plugin topic 被发现。用户无需本地链接（ADR-0003）。
- 一个 **skill** 随插件一起发布并由宿主半边注册，这样模型知道何时调用工具、如何解析默认值，以及如何表述指标推荐。
- 它**全部是 TypeScript**；宿主半边运行在 DSH 进程中，客户端半边运行在页面中。没有 Python sidecar。

### 模块接缝 (Module seams)
- **`MarketDataProvider`**（接口）：`fetchCandles(symbol, interval, range)` 和 `fetchDerivatives(symbol)`。实现：**BinanceProvider**（主要）和 **HyperliquidProvider**（补充）。这是唯一的外部 I/O。
- **`buildMarketView(request, provider)`**（纯编排，主要接缝）：解析请求并返回一个 **`MarketView`** = `{ chartSpec, indicators, candidates, ruleSignals, context }`。所有确定性的东西都挂在这一个入口点上。
  - `candidates` = swing pivots、支撑/阻力区、斐波那契价位、均线排列、走势线/通道。
  - `ruleSignals` = 交叉、超买/超卖、价位突破。
  - `context` = **市场状态**：走势强度（例如 ADX）、区间与趋势之别、波动率（ATR / 布林带宽度）、成交量状态、均线排列。
  - 模型的筛选、命名、推荐和结论**不**在其中。
- **`chartSpec`** 是唯一的可序列化宿主↔客户端契约，通过工具的 presentation metadata 交付给客户端。它描述窗格、series、叠加层、marker、未收盘 K 线标志以及周期集合。
- **`chartSpec → Lightweight Charts series`** 是客户端上的纯映射函数；React 组件是一个很薄的渲染器。

### 数据 (Data)
- 市场：**加密**。**Binance 现货**是主要的 OHLCV 骨干（可分页的深厚历史、无需 API key）；**Hyperliquid** 作为补充，用于原生永续指标和 HL 上市的资产。Hyperliquid 每个市场的历史被限制在约 5,000 根 K 线（1h 周期约 208 天），因此长回看由 Binance 提供。
- 周期：**15m / 1h / 4h / 1d**，默认 **1h**。时间词选择主要周期（今天 → 1h，这周 → 4h，这月 → 1d），共振周期是再上一级（1h → 4h；1d → 1w，仅为更高角色而添加）。
- 响应按周期缓存并使用较短的 TTL；Binance 的速率限制响应会触发带重试上限的指数退避。
- 分析**只使用已收盘 K 线**；未收盘 K 线会显示，但永远不会用于产生信号、结构或形态判断。

### 指标 (Indicators)
- 指标引擎：**trading-signals**（MIT）。覆盖：MA/EMA、MACD、RSI、布林带、KDJ（通过随机指标的 J 线）、ATR、成交量。
- 参数是构造函数参数：合理的默认值，加上以自然语言表达的按对话覆盖。
- 默认呈现：价格窗格上的 MA20/50/200；MACD、RSI 和成交量作为子窗格；布林带、KDJ 和 ATR 可开关。

### 分析 (Analysis)
- **分层信号**：规则信号（机械）→ 结构/形态判断（模型）→ 综合结论（模型）。
- **分工**：机械层产生候选；模型负责筛选、命名结构与形态、推荐指标，并撰写结论（ADR-0002）。
- 优先级：走势结构与支撑阻力/斐波那契优先；经典形态次之；艾略特最后。
- **多周期共振**：更高周期确定结构/方向，当前周期确定时机。
- 每个结论都带有**方向 + 失效位 + 置信度（高/中/低）**。此阶段没有入场/出场目标，也不提供投资建议。
- **指标推荐**是源自 `context` 的建议性文本；在用户接受之前，它绝不会改变已渲染的图表。

### 意图行为 (Intent behaviour)
- 模糊请求无需询问即可解析：symbol → 其主要现货交易对；周期 → 由时间词得出，或默认 1h；指标 → 主流默认集。解析出的选择会在回复中说明。
- 只有当 symbol 无法解析时，agent 才提问。
- 后续追问继承该对话的 symbol 及其他上下文。

### 感知 (Perception)
- 默认：模型基于数值化的 `MarketView`（指标、候选、规则信号、上下文）进行推理。这在任何模型路由上都能工作。
- 可选视觉：当路由声明支持图像输入时，宿主可以把同一份 `chartSpec` 栅格化为 PNG，并作为图像内容块附加，以便模型检视形态。这是一种混合方式：以数值为主，按需提供图像。
- 当路由仅支持文本时，图像路径会被静默跳过，改用数值路径（ADR-0003）。

### 明确排除项 (Explicit exclusions)
- 不使用 TradingView 行情，也不使用 TradingView MCP：DSH 的 MCP 客户端没有 OAuth，且 TradingView 的 ToS 禁止非展示性/算法化使用以及第三方依赖其数据（ADR-0004）。
- 不使用 TradingView Advanced Charts：其许可禁止开源项目和再分发，而本插件是开源的（ADR-0001、ADR-0003）。
- 图表使用 **Lightweight Charts**（Apache-2.0）并喂入我们自己的数据，同时保留 TradingView attribution（ADR-0001）。

## 测试决策 (Testing Decisions)

- 好的测试断言**外部行为**，而不是实现细节：给定一个请求和固定的 K 线序列，被断言的是产出的 `MarketView`（或 provider 输出，或图表映射）。没有测试会深入指标内部或私有辅助函数。
- **接缝 1 — `buildMarketView`**：主要的行为接缝。测试通过一个内存中的 `MarketDataProvider`，用固定的 OHLCV fixture 驱动它，并断言 `chartSpec`、`indicators`、`candidates`、`ruleSignals` 和 `context`。这覆盖意图默认值、周期映射、指标参数、结构/价位检测、规则信号、市场状态分类、仅用已收盘 K 线的行为，以及多周期共振。
- **接缝 2 — `MarketDataProvider`**：每个实现都针对录制的 HTTP fixture 进行测试，覆盖解析、分页、interval 处理、范围边界和速率限制退避。测试中不进行实时网络请求。
- **接缝 3 — 图表契约**：直接测试纯的 `chartSpec → series` 映射；React 组件最多只有一个冒烟渲染测试。
- 机械检测器的正确性以**参考值**为基准（例如指标输出与已知参考序列交叉核对），而不是以自身为基准。
- 本仓库**没有先例**（全新项目）。把测试运行器（Vitest）和 fixture 约定作为第一个工单的一部分建立起来。

## 范围之外 (Out of Scope)

- 交易执行、下单、仓位规模计算，或任何券商/交易所的写入 API。
- 回测、策略优化或机器学习。
- 投资组合跟踪、盈亏，或跨资产筛选器。
- 非加密市场（美股、A 股、外汇、期货）。
- 第一阶段的艾略特波浪分析（有意放在最后）。
- 定时/告警驱动的主动扫描：第一阶段是一问一答；定期扫描器是更晚的交互模式。
- 资金费率/未平仓量指标（推迟到以永续合约为重点的阶段）。
- 为启用视觉而更改用户的 harness 模型配置：这仍是需要用户自行执行且有文档记录的步骤。
- 重新实现 TradingView Advanced Charts 的行为（画线工具、100+ 内置指标）——因许可和 ADR-0001 而被排除。

## 补充说明 (Further Notes)

- 记录在案的决策：ADR-0001（图表渲染）、ADR-0002（分析分工）、ADR-0003（开源 MIT npm 插件）、ADR-0004（不使用 TradingView 数据或 MCP）。
- 支撑调研：行情数据源、加密数据 API（Binance/Hyperliquid）、TypeScript 指标库，以及 DSH 插件集成指南。
- 两个必须围绕其设计的硬约束：Hyperliquid 将每个市场的历史限制在约 5,000 根 K 线；且模型路由可能仅支持文本，因此视觉必须始终可选。
- 插件必须保持零密钥即可分享：Binance 和 Hyperliquid 的公开读取无需 key，且不得随包再分发任何行情数据。
- 宿主↔客户端契约就是图表规格；保持其可序列化，正是让两半以及（可选的）栅格化器能够独立开发和测试的原因。
